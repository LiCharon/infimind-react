# 法飞飞 AI 合同工作台：一键生成界面设计方案

> 当前项目完成态：`合同审查与批注` + `合同智能起草` 两个产品页，共用一套对话工作台外壳。
>
> 版本同步：2026-08-07。本文已覆盖 Enter 发送、起草意图路由与可重复生成、扩展附件解析和 OCR 预处理。
>
> 目标：将本文末尾的“一键生成指令”直接交给 AI 编码工具，即可生成一套结构、状态与视觉纪律都接近当前项目的 React 前端；在其他专业文档类 AI 产品中，仅替换领域文案、交付物和数据字段即可复用。

---

## 1. 产品定义

这是一个 **文档优先、对话驱动、任务可回溯** 的专业 AI 工作台，不是仪表盘，也不是普通客服聊天界面。

用户的操作路线固定为：

```text
创建/选择任务 → 输入要求或上传参考文件 → 查看流式处理过程 →
在对话中获得交付卡 → 打开右侧正式文档 → 复制、下载或返回继续补充 →
提出追问或明确要求更新全文 → 得到解释或下一版文档
```

两种业务模式共享外壳，但交付物不同：

| 模式 | 路由 | 对话内交付物 | 右侧文档列 |
| --- | --- | --- | --- |
| 合同审查与批注 | `/contract-rewrite` | “商业合同审查批注稿”卡片 | 原文 + 最小问题片段高亮 + 就近修订卡 |
| 合同智能起草 | `/contract-draft` | 对话回复或可多次生成的“合同初稿”卡片 | Markdown 合同正文 + 待确认信息面板 |

设计语言必须统一：用户从“审核”切换到“起草”时，应感觉自己仍在同一个法务助手，而非跳转到另一套产品。

## 2. 总体视觉方向

### 2.1 关键词

克制、专业、可信、阅读优先、低干扰、文档工具感。

避免：深色科技感背景、大面积渐变、玻璃拟态、仪表盘卡片矩阵、彩色统计图、头像气泡墙、过多胶囊标签和多层圆角容器。

### 2.2 设计令牌

```css
:root {
  --chat-text: #161616;       /* 主文字 */
  --chat-muted: #9A9A9E;      /* 辅助文字 */
  --chat-line: #ECECEC;       /* 分割线 */
  --chat-soft: #F7F7F8;       /* 侧栏、弱化背景 */
  --chat-selected: #FFFFFF;  /* 选中历史项 */
  --chat-accent: #FD7002;     /* 品牌强调、处理中、定位 */
  --chat-action: #202024;     /* 发送、充值等强操作 */
  --risk-high: #C0392B;
  --risk-mid: #FD7002;
  --risk-low: #B8860B;
  --success: #198754;
}
```

- 字体：`Inter, -apple-system, BlinkMacSystemFont, "PingFang SC", "Microsoft YaHei", sans-serif`。
- 页面正文：`16px / 1.82`；合同正文：`16px / 1.95`。
- 顶栏标题：`16px / 650`；免责声明：`11px`。
- 输入器圆角：`24px`；任务/交付卡：`15px`；列表项：`10px`；小标签：`7–9px`。
- 阴影只用于固定输入器、选中会话和浮层。普通阅读内容以留白与细分割线组织，不堆叠卡片。

### 2.3 桌面版精确尺度

| 部位 | 尺寸与规则 |
| --- | --- |
| 应用高度 | `100vh`，页面本身不纵向滚动 |
| 历史侧栏 | `286px` 宽、`16px` 内边距、`#F8F8F9` 背景 |
| 顶栏 | 高 `76px`，底部 1px `#ECECEC` 分隔线 |
| 对话内容 | 最大宽 `860px`，左右随容器居中，底部预留 `162px` |
| 固定输入器 | 最大宽 `860px`、最小高 `118px`，固定于**当前对话列**底部 |
| 文档展开态 | 左对话列 `38%`、最小 `420px`；右文档列占其余宽度 |
| 右侧文档 | 正文最大宽 `980px`；滚动区左右留白 `clamp(45px, 7vw, 120px)` |

中等屏幕（`<=1100px`）把侧栏改为 `230px`，展开态聊天列改为 `42%`、最小 `360px`。移动端（`<=760px`）隐藏侧栏，文档进入全屏。

### 3.1 共享状态模型

```ts
type WorkspaceThread = {
  id: string
  title: string
  messages: Message[]
  updatedAt: number
}

type RequestState = {
  loading: boolean
  stage?: string
  error?: string
}

type Message = {
  id: string
  role?: 'user' | 'assistant'
  type?: 'user' | 'assistant' | 'draft'
  content: string
  files?: Array<{ name: string; size: number }>
  status?: string
```

## 4. 组件规范

### 4.1 `SidebarShell`：历史、任务和账户

**搜索框**

- 高 `42px`，灰底 `#EDEDEE`，圆角 `12px`。
- 左侧使用 `History` 图标，输入提示为“搜索历史对话”，右侧显示淡灰 `⌘ K`。
- 输入框无边框和阴影；焦点仅让文字可编辑，不制造明显蓝色浏览器描边。

**品牌区与动作按钮**

- `public/logo.png` 放在 `27 × 27px` 的白色圆形容器中；右侧“法飞飞”17px。
- 两个主动作均是无背景文字按钮：`PenLine + 新对话`，`FolderOpen + 新审查任务/新起草任务`。
- 高 `48px`，左右 `13px`，图标与文字间距 `13px`；hover 仅填充 `#EFEFEF`。

**历史列表**

- 列表标题为 13px 灰字，距动作区上方 25px。
- 每个条目高约 42px，左侧 `MessageCircle` / `FolderOpen`，中间省略的标题，右侧删除图标。
- 选中项白底、`0 2px 8px rgba(0,0,0,.04)` 阴影；默认删除图标透明，hover/选中后显示。
- 进行中：图标橙色旋转，背景可轻微偏暖；禁止删除。

**余额入口与浮层**

- 固定在侧栏底部，顶部使用细灰线隔开。
- 收起态是 `66px` 高的浅灰圆角账户触发器，包含深蓝“法”字圆形头像、名称、下拉箭头。
- 点击后在其上方弹出 `balance-popover`：白底、20px 圆角、轻阴影；包含头像标题栏、`CircleDollarSign + 剩余用量 + 刷新`、余额浅灰信息块、可用状态、深色“充值用量”按钮。
- 余额状态必须包含加载、错误、无 CNY 数据和可用/不可用四种状态。

### 4.2 `ChatHeader`：少工具、强定位

```text
[侧栏开关] [返回首页]        当前任务标题
                               AI 生成内容仅供参考，请结合实际情况判断
```

- 使用三列 Grid：`1fr auto 1fr`，标题永远居中。
- 左侧图标按钮命中区 `36 × 36px`；不得把复制、导出等文档工具堆在此处。
- 文档展开时，左侧仅保留“返回对话”箭头，标题左对齐；导出工具移动到右侧文档栏。

### 4.3 `Conversation`：不是客服气泡墙

**空态**

- 内容区域从顶栏下方约 `48px` 开始；最大宽仍为 860px。
- 首段为左对齐、不带头像的专业说明。审核示例强调“上传合同、梳理风险、生成批注稿”；起草示例强调“描述类型、背景、关键要求，生成可编辑初稿并提示待确认信息”。
- 下方放 2–3 个浅灰推荐按钮，按钮只包裹内容宽度，圆角 `13px`，右侧有 `→`。推荐项不是卡片网格。

**用户消息**

- 右对齐，最大宽 78%，内容气泡为 `#F3F3F4`，圆角 `16px`，内边距 `13px 17px`。
- 文件不塞进气泡：在气泡下方独立显示 `attached-file` 条，白/极浅灰底、细边框、文件图标、名称、体积；长文件名省略。

**AI 消息和状态**

- AI 消息左对齐、无头像、无彩色气泡，用 Markdown 排版呈现，使输出像专业意见书或正式起草说明。
- 处理中使用一行灰色文字 + `Loader2`，例如“正在识别合同类型并加载专项条款框架…”。
- 错误用低饱和浅红背景，13px 文本，不使用全屏遮罩。
- 流式输出时默认跟随底部；用户主动上滑后停止自动滚动，回到底部附近后再恢复。
- 起草页已有草稿后，普通提问仅渲染 AI Markdown 回复；只有意图被识别为“起草、重写、更新、重新生成完整文档”时才出现新的合同初稿交付卡。不得把每一句追问都误生成为一份完整合同。

### 4.4 `Composer`：固定但不遮挡内容

```text
┌──────────────────────────────────────────────────────────┐
│ 上传合同或输入你特别关注的审查重点…                       │
│ [已选文件 ×] [已选文件 ×]                                │
│  +  |  审查：快速 / 深度思考 / 更多          [发送箭头]  │
└──────────────────────────────────────────────────────────┘
```

- 放在当前聊天列底部，外层使用从透明到白色的渐变，避免把滚动内容硬切断。
- 主容器：白底、1px `#E5E5E6`、24px 圆角、`0 8px 28px rgba(0,0,0,.10)` 阴影。
- 文本框无边框、最小高 `44px`、16px 字号；**Enter 发送，Shift + Enter 换行**。输入法组合态不得触发发送；`Cmd/Ctrl + Enter` 也应保持可发送。
- 发送按钮为 `42 × 42px` 深色圆形，禁用时为浅灰。
- 文件限制文案与实现一致：PDF、DOC/DOCX、RTF、ODT、Excel、PowerPoint、TXT/Markdown/CSV/JSON/XML/HTML，以及 PNG/JPG/WebP/BMP/TIFF/GIF；最多 6 个；单个不超过 80MB。

**模式差异**

| 审查页 | 起草页 |
| --- | --- |
| 上传按钮 + 分隔线 + “快速 / 深度思考”分段控件 + 更多 + 发送 | 上传按钮 + 发送；不展示模型名称或策略标签 |
| 占位语：“上传合同或输入你特别关注的审查重点…” | 占位语：“上传参考文件或输入你想起草的合同要求…” |

### 4.5 `TaskModal`：创建可回溯任务

- 全屏半透明黑色遮罩（约 22%），中心白色 440px 弹窗、17px 圆角、轻边框。
- 内容：标题与关闭图标、任务名称 input、要求 textarea、12px 灰色说明、取消和深色创建按钮。
- 审查页字段为“审查要求”；起草页字段为“起草要求”。
- 点击遮罩关闭，点击弹窗内部不关闭，首个输入框自动聚焦。

### 4.6 `DocumentDeliveryCard`：对话到正式文档的唯一主入口

- 审查完成或起草完成后嵌在 AI 消息中。
- 最大宽 `530px`，最小高 `116px`，白底、细灰边框、15px 圆角、左侧 25px 蓝色文档图标。
- 标题单行省略；副标题显示关键信息：
  - 审查：问题数、就近标记数、点击展开文档。
  - 起草：合同初稿、待确认项数量、点击展开文档。
- 不用醒目的大按钮；整张卡片可点击。

## 5. 两类正式文档列

### 5.1 审查与批注：原文定位优先

右侧文档列仅保留 `复制`、`下载 Word`、`关闭` 三项工具。合同原文必须保持阅读节奏，不能被一长列风险卡取代。

**可信定位时：行内标记 + 局部修订卡**

```text
原句：……最小问题子句①……

①  改为  建议替换的最小文本
   查看批注与完整修订条款 ▾
```

- 只标记最小问题子句：透明至 54% 的橙色底、1.5px 橙色下划线、上标圆形编号。
- 绝不整行涂色、整条条款涂色或用大面积波浪线。
- 修订卡与原文左侧约缩进 22px；白橙底、细边框、10px 圆角。
- 第一行只显示“改为 / 删除此处 / 在此后补充 + 短建议”；原片段、解释、完整修订条款放入折叠区。
- 高中低风险只微调编号、边线和底色，不改变结构。

**定位不可信或新增条款时：紧凑修订卡**

- 不伪造高亮；卡片挂在可信插入锚点之后。
- 实线左边线 = 修改，虚线 = 新增，双线 = 删除。
- 显示操作类型、标题、两行预览；完整内容折叠。

### 5.2 智能起草：正文优先 + 待确认信息

- 文档正文是正式中文合同 Markdown，使用 16px / 1.95，标题居中且有宽松留白。
- 右上侧（大屏）放 `待确认信息` 面板：约 210px 宽、淡橙白底、细边框；列表中每项可确认，“全部确认”是描边按钮。
- 移动端与中等屏幕将该面板退化到正文上方的完整宽度区块。
- 文末放浅灰“起草说明”：AI 草稿仅供参考，签署前核对主体、授权、金额、期限、税务、公司治理与专项事实。
- 当前后端会显示“正在识别合同类型并加载专项条款框架”；高风险类型（劳动、股权、工程、借款、租赁、数据、知识产权、婚姻家事等）在待确认项中强化专业复核。
- **可重复交付规则**：首次输入或上传新参考材料默认进入文档生成；已有草稿时，普通问答留在对话列，明确要求“按补充信息更新全文”“重新生成一版”“重写合同”等才生成新初稿。新初稿出现后应保留旧对话记录，并让右侧始终展示最新完整草稿。

## 7. 响应式、可访问性与验收规则

1. `<=760px` 隐藏历史侧栏；打开文档后改为全屏文档，顶部始终有关闭返回按钮。
2. 所有纯图标按钮命中区至少 36px，并提供 `aria-label`；上传、发送、复制、下载、关闭均可键盘访问。
3. 长标题、会话名称和文件名必须省略，不挤压删除图标；合同正文使用 `word-break: break-word`。
4. 文件、余额、流式生成、空态、错误态、删除禁用态必须都可见并有明确文案。
5. 审查页只有服务端提供有效 `quoteSpans` 时才能标记原文；定位失败时必须降级为紧凑修订卡。
6. 不要将模型名称显式塞进起草页输入器；起草页工具栏只保留上传入口和发送。
7. Enter 发送、Shift+Enter 换行；中文输入法候选组合期间不得发送。
8. 附件白名单、前端文件选择器和服务端校验必须完全一致；未知格式要在上传后得到明确错误，而不是静默丢弃。
9. 图片 OCR 必须在加载态提示“正在识别图片文字”；低清/倾斜扫描件可提示用户上传更清晰原件，但不应因预处理失败直接中断 OCR。

## 9. 快速验收清单

- [ ] 审查与起草页看起来属于同一套产品，侧栏和输入器尺寸、颜色、圆角完全一致。
- [ ] 用户可新建任务、搜索会话、切换会话、删除非进行中会话、上传附件、查看余额。
- [ ] 起草页没有可见的模型名称；审核页仍保留策略切换。
- [ ] 流式状态说明当前动作，不用全屏加载。
- [ ] 审查稿只标记可定位的最小原文片段；定位失败不高亮。
- [ ] 起草稿提供待确认信息、复制、Word 下载和起草说明。
- [ ] 已有草稿后询问条款含义不会生成第二份全文；明确要求重新生成会出现最新初稿卡。
- [ ] Enter 可发送，Shift+Enter 可换行，输入法候选状态不误发。
- [ ] 扩展格式在文件选择器、附件标签与服务端错误反馈中表现一致；低置信度图片 OCR 不阻断会话。
- [ ] 展开文档后仍可通过左侧聊天理解上下文。
- [ ] 手机端可完整返回对话，固定输入器不遮挡内容。
